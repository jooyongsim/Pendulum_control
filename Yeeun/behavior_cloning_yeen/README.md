# behavior_cloning_yeen — 회전형 역진자 swing-up 행동 복제 (behaviour cloning)

`simulator/rotary_swingup_realtime.py` 의 전문가 컨트롤러를 교사로 삼아, 같은 일을 하는
신경망 정책을 지도학습으로 만든다.

- **교사 (expert)**: `rotary_model.SwingUp` — 에너지 펌핑 + catch + 4상태 극점배치 균형제어로
  이루어진 **상태 기계**. 실기(`swing-up/swingup_control.py`)에서 돌아가는 바로 그 제어기다.
- **학생 (policy)**: MLP. 관측 → 팔 가속도 명령 `u` 를 직접 회귀한다.
- **학습 방식**: behaviour cloning. 전문가 궤적 위의 `(관측, 행동)` 쌍에 MSE 회귀. 보상 없음.

```powershell
conda activate control2026
cd "$env:USERPROFILE\OneDrive\바탕 화면\딥러닝\Pendulum_control"
$env:PYTHONPATH="$PWD\behavior_cloning_yeen"

python behavior_cloning_yeen/collect_expert.py --episodes 250     # 전문가 시연 수집  (~2분)
python behavior_cloning_yeen/train_bc.py --compare --plot         # h=1, h=5 학습     (~4분)
python behavior_cloning_yeen/dagger.py --iters 3                  # DAgger 3 반복     (~9분)
python behavior_cloning_yeen/eval_bc.py --episodes 120 --plot `
    --ckpt behavior_cloning_yeen/checkpoints/bc_h5.npz behavior_cloning_yeen/checkpoints/dagger_h5_iter3.npz
```

> 평가는 **120 플랜트 이상**으로 돌릴 것. 40 플랜트에서는 정책 간 차이가 노이즈에 묻힌다
> (아래 "표본 크기 주의").

## 관측 / 행동 정의

제어 루프가 제어기에 넘겨주는 값을 **그대로** 관측으로 쓴다. 즉 양자화된 엔코더(0.3°),
필터링된 `θ'`, 4 ms 지연이 모두 포함된 "실기에서 실제로 볼 수 있는" 값이다.

| | 정의 | 차원 |
|---|---|---|
| 관측 `z` | `[θ, θ', φ, φ']` (`Loop` → 제어기) | 4 |
| 특징 `feat` | `[sinθ, cosθ, θ', φ, φ']` | 5 |
| 행동 `u` | 팔 가속도 명령 [rad/s²], `±ACCEL_MAX` 로 클립 | 1 |

`θ` 를 `sinθ, cosθ` 로 바꾸는 이유: `θ` 는 `±π` 에서 감싸므로(wrap) 매달린 상태 바로 근처에서
입력이 `+180° ↔ -180°` 로 점프한다. 네트워크 입장에서는 물리적으로 같은 자세가 입력 공간의
정반대 끝에 놓이는 셈이라 학습이 깨진다. `sin/cos` 는 그 불연속을 없앤다.

## 핵심 문제: 전문가는 memoryless 가 아니다

전문가는 관측에 없는 내부 상태를 들고 있다.

| 내부 상태 | 역할 | 관측에 있나 |
|---|---|---|
| `mode` (`swing`/`balance`) | 제어 법칙 자체를 바꿈 | ✗ |
| `tr` (경과 시간) | 처음 0.15 s `+30`, 다음 0.15 s `-30` (개루프 bang-bang) | ✗ |
| `phi_ref` | catch 시점의 팔 각도, 3 s 로 지수 감쇠 | ✗ |
| `b_hat` | 엔코더 영점 오차 추정 | ✗ |

따라서 `u = π(z)` 형태의 memoryless 정책은 전문가를 **원리적으로** 복제할 수 없다.
같은 `(θ, θ', φ, φ')` 가 swing 모드에서는 `u ≈ +30`, balance 모드에서는 `u ≈ -5` 를
정답으로 갖는 구간이 존재하고, MSE 회귀는 그 둘을 평균내 버린다.

→ 과거 `K` 프레임을 쌓아(frame stacking) 궤적의 모양에서 숨은 모드를 암묵적으로 추론하게 한다.
`--history 5` (50 ms) 가 기본값이고, `--history 1` 이 비교용 baseline 이다.

**이걸로도 못 고치는 것**: 초기 bang-bang 반전 시점은 절대시간 `tr` 의 함수라서 50 ms 창으로는
복원이 안 된다. `tr` 을 관측에 넣거나 GRU/LSTM 으로 전체 이력을 요약해야 한다.

## 데이터 수집 설계

`collect_expert.py` 는 무작위화된 플랜트에서 전문가를 돌리고 모든 제어 tick 을 기록한다.
무작위화 범위는 `rotary_swingup_realtime.py --check` 의 robustness 스윕과 같다.

| 항목 | 범위 |
|---|---|
| `b` (팔 결합) | 0.8 – 1.2 × 공칭 |
| Coulomb 마찰 | 0.5 – 2.0 × |
| 루프 지연 | 4 – 12 ms |
| 초기 기울기 | ±2.5° |
| 엔코더 영점 | ±0.5° |
| 외란 kick | 70% 확률, 1–3 회, 3–9 rad/s |

**외란을 일부러 세게 넣는다.** 깨끗한 swing-up 만 본 정책은 궤도를 벗어난 순간 할 줄 아는 게
없다. kick 이 `fall` 임계(30°)를 넘기면 전문가가 다시 swing 하므로, 그 복구 데이터가 쌓인다.

에피소드 채택 기준은 "전문가가 한 번이라도 잡았는가"(`t_catch is not None` 且 정지 없음)다.
마지막 5 s 를 보는 `success` 로 걸러내면, 늦은 kick 에서 복구하는 에피소드가 — 정확히 우리가
원하는 데이터가 — 버려진다.

## 학습

- MLP `[5K → 256 → 256 → 1]`, ReLU, Adam `1e-3`, cosine annealing, 80 epoch
- 정규화된 행동에 대한 MSE. swing 모드 샘플에 `--swing-weight 2.0` 가중 (희소하고 어려움)
- **검증 분할은 에피소드 단위.** 10 ms 간격 샘플은 거의 동일해서, 샘플 단위로 무작위 분할하면
  훈련/검증 양쪽에 사실상 같은 데이터가 들어가고 검증 오차가 아무 의미를 갖지 않는다.
- 체크포인트는 가중치 + 정규화 상수만 담은 `.npz`. 추론은 `il_common.NumpyMLP` 로 numpy 만
  쓴다 — 실기를 돌리는 호스트 루프에 torch 를 깔 필요가 없게 하려는 것.
- `check_numpy_matches_torch()` 가 매 학습마다 torch 출력과 numpy 출력을 비교한다
  (가중치 추출 순서 버그 + 아래 OpenMP workaround 의 수치 손상을 동시에 잡는 장치).

## 평가

`eval_bc.py` 는 정책을 **제어 루프에 직접 넣어** 돌린다. open-loop RMSE 는 약한 지표다:
BC 의 실제 실패 양상은 covariate shift — 작은 행동 오차가 전문가가 가본 적 없는 상태로
플랜트를 밀어내고, 거기서는 학습 데이터가 없어 오차가 누적된다. 이건 정책이 직접 운전할
때만 드러난다.

모든 정책은 **같은** 무작위 플랜트 집합에서 평가되며(paired), 시드는 수집 시드와 분리되어 있다.

| suite | 외란 | 길이 | 측정 대상 |
|---|---|---|---|
| `clean` | 없음 | 15 s | 매달린 상태에서 세워 유지할 수 있는가 |
| `disturbed` | 1–2 회, 3–7 rad/s | 25 s | 넘어진 뒤 다시 세울 수 있는가 |

성공 = 마지막 5 s 의 95% 이상을 상향 10° 안에서 유지.

> `disturbed` suite 의 외란은 수집용보다 약하고 더 일찍 들어간다. 수집은 "넘어짐 데이터"가
> 목적이라 세게 늦게 때리지만, 평가에서 그러면 다시 안정될 시간이 없어 **외란의 가혹함**을
> 재는 지표가 된다 (전문가조차 50% 가 나왔다).

## 결과 (250 에피소드 수집 / 206 채택 / 309,206 샘플, 80 epoch)

### open-loop 적합도 — 검증 에피소드, rad/s²

| | 입력 | 파라미터 | RMSE | swing | balance | R² |
|---|---|---|---|---|---|---|
| `bc_h1` (memoryless) | 5 | 67,585 | 2.552 | 3.993 | 1.941 | 0.959 |
| `bc_h5` (history) | 25 | 72,705 | **2.070** | **3.451** | **1.437** | **0.973** |

전문가 행동의 표준편차는 12.5 rad/s². history 쪽이 모든 항목에서 낫고, 특히 balance 모드에서
26% 개선된다 — 모드 모호성의 손해가 주로 balance 에서 발생한다는 뜻이다.

`--history 30` (300 ms) 도 같은 데이터·같은 epoch 으로 학습해 봤으나 **더 나빴다**
(RMSE 2.371, balance 1.581). 평평한 MLP 에 30 프레임을 통째로 주어도 느린 상태를 알아서
적분해내지는 않는다. 입력 차원만 6 배가 되어 같은 데이터로 학습하기 어려워질 뿐이다.

### 읽는 법

1. **swing-up 자체는 완전히 복제된다.** 모든 정책이 `caught ~100%`, catch 시각도 2.4 s 로 동일.
   `figs/bc_closed_loop.png` 의 θ 궤적은 눈으로 구분이 안 된다.
2. **history 는 swing-up 에서만 낫다.** 외란 없는 suite 에서는 87.5% → 93.3% 이고
   팔 최대각도 81.2° → 61.4° 로 크게 줄지만, **외란 suite 에서는 순서가 뒤집힌다**
   (`bc_h1` 72.5% > `bc_h5` 68.3%). 두 정책의 팔 최대각은 외란 하에서 거의 같고
   (112.4° vs 112.8°) 정지 사유도 모두 ARM LIMIT 이다. 50 ms history 는 깨끗한
   스윙업의 모드 모호성을 줄여주지만, 넘어진 뒤 팔이 밀린 상태는 애초에 데이터가
   없으므로 관측을 늘려도 답이 없다. 그걸 고치는 것이 DAgger 다.
3. **남는 실패는 전부 팔 각도다.** 모든 정지 사유가 `ARM LIMIT (140 deg)` 하나뿐이다.
4. **DAgger 가 그 팔 문제를 고친다.** arm max 중앙값 61.4° → 55.3° (전문가 56.0°),
   외란 suite 에서 68.3% → 75.8% (전문가 77.5%). 아래 참조.

### 표본 크기 주의

처음에는 40 플랜트로 평가했고 `bc_h5` 가 97.5%, DAgger 가 92.5–95% 로 나와
"DAgger 가 성능을 떨어뜨렸다" 고 판단했다. **틀린 결론이었다.** 40 플랜트에서 97.5% 는 실패가
1 건뿐이라 개선 여지가 측정되지 않는 천장 효과이고, 39/40 과 38/40 의 차이는 이항 노이즈다.
120 플랜트로 늘리자 순서가 뒤집혀 DAgger 가 단조 개선으로 나타났다.
**이 과제에서 40 플랜트는 정책 비교에 부족하다.**

### 왜 팔이 밀리는가

`figs/bc_closed_loop.png` 가운데 패널을 보면, 전문가는 팔이 0° 근처로 수렴하는데 BC 는
한쪽으로 치우친 채 더 큰 진폭으로 진동한다. 원인은 관측 설계에 있다.

전문가의 balance 법칙은 `u = -K·[θ-b̂, θ', φ-φ_ref, φ']` 이고 `φ_ref` 는 catch 시점의 팔 각도에서
**3 s 시정수로 감쇠**한다. 정책은 `φ_ref` 를 볼 수 없으므로, 같은 `φ` 에 대해 서로 다른 `u` 가
정답인 상황을 평균낸 값을 학습한다 → 편향된 팔 평형점. 50 ms history 로는 3 s 짜리 감쇠
상태를 추정할 수 없다.

## DAgger (`dagger.py`)

BC 는 **전문가가 방문하는 상태**만 본다. 복제된 정책의 작은 오차가 진자를 전문가가 간 적 없는
상태로 밀어내고, 거기에는 학습 신호가 없다. 이것이 covariate shift 이고 위의 팔 편향이 그
구체적 발현이다.

```
반복마다:
    정책이 플랜트를 운전      -> 정책 자신의 상태 분포를 방문
    전문가가 같은 관측을 관찰 -> 그 상태들에 라벨을 붙임
    데이터셋에 합치고 처음부터 재학습
```

### 상태 기계인 전문가를 어떻게 질의하는가

교과서적 DAgger 는 "정책이 방문한 상태 `s` 에 `π*(s)` 를 질의한다" 지만, 여기 전문가는 순수
함수가 아니다 (`mode`, `tr`, `phi_ref`, `b_hat`). 임의의 상태를 던져 물을 수 없다.

대신 **shadow 실행**한다 (`ShadowExpert`). 매 제어 tick 마다 정책과 전문가를 **둘 다** 호출하고,
플랜트에는 정책의 명령만 적용한다. 전문가는 운전하지 않지만 같은 관측 스트림을 보며 자기
내부 상태를 갱신하므로, 그 내부 상태가 정책이 실제로 만든 궤적을 따라 진화한다. 그래야 라벨이
의미를 갖는다.

`beta` (전문가 개입 비율) 기본값은 0 이다. iteration 0 인 기존 expert 데이터셋이 이미 β=1
라운드에 해당하고, 시작 정책이 충분히 멀쩡해 개입 없이도 라벨이 쓸모 있는 상태에 머문다.

### 반복 경과 (40 플랜트 평가, 참고용)

| | 데이터 | 정책 자신의 상태에서의 격차 | 학습 후 RMSE (전문가 상태) |
|---|---|---|---|
| iter 0 (BC) | 309,206 | – | 2.070 |
| iter 1 | 363,073 | 3.261 | 2.622 |
| iter 2 | 415,768 | 4.104 | 2.536 |
| iter 3 | 470,818 | 3.756 | 3.360 |

"정책 자신의 상태에서의 격차" 는 DAgger 롤아웃 중 정책이 하려던 행동과 전문가 라벨의 RMSE 다.
BC 의 검증 오차가 구조적으로 볼 수 없는 양 — `bc_h5` 는 전문가 궤적 위 balance RMSE 가 1.437
인데, 자기 궤적 위에서는 2.9–3.8 로 2 배 이상이다. 그게 covariate shift 의 직접 측정값이다.

### open-loop 지표의 함정

`dag_i3_h5` 는 **open-loop RMSE 가 가장 나쁘고 (3.360 vs 2.070) closed-loop 성능이 가장 좋다.**
DAgger 데이터셋은 반복마다 어려운 상태가 섞여 들어가므로 전문가 궤적 위에서 잰 적합도는
나빠지는 게 정상이고, 정작 중요한 것은 정책이 직접 운전할 때의 성공률이다.
**open-loop RMSE 로 모델을 고르면 안 된다.**

### 남은 격차

DAgger 3 회 후에도 전문가에 닿지는 못했다 (95.8% vs 99.2%, 75.8% vs 77.5%). 격차 지표도
단조 감소하지 않았다 (3.261 → 4.104 → 3.756). DAgger 는 **가본 적 없는 상태**를 고치지만
**볼 수 없는 상태**는 고치지 못한다. `φ_ref` 는 관측에 없고, 데이터를 더 모아도 같은 관측에
다른 정답이 붙는 구조는 남는다. 이를 더 줄이려면 관측 설계를 바꿔야 한다 — `φ` 의 저역통과
값을 명시적 특징으로 넣거나(시정수를 직접 주입), GRU/LSTM 으로 이력을 요약하거나.

## 알려진 제약

- **arm 편향**: 남아 있는 실패의 전부다. DAgger 가 상당 부분 줄였으나 완전히 없애지는
  못했다. 관측에 팔 기준각을 복원할 단서를 넣는 것이 남은 대응이다 — 단, 단순히 history 를
  늘리는 것(`--history 30`)은 효과가 없음이 확인되었다.
- **불연속 복제 실패**: swing 모드의 `sign(θ'·cosθ)` 는 상태의 불연속 함수다. MSE 회귀는
  전환면 근처에서 `±pump` 를 평균내 0 쪽으로 뭉갠다. 분류 헤드로 부호를 따로 예측하거나
  분포형 정책(mixture / diffusion)을 쓰는 것이 정석적 대응이다.
- **시뮬레이션 전용.** `data/swingup_*.csv` 의 실기 로그는 아직 쓰지 않았다.
- **전문가를 넘어서지 못한다.** BC 도 DAgger 도 전문가 모방이 상한이다. 전문가보다 잘하려면
  보상을 정의하고 RL 로 미세조정해야 한다.

## 환경 메모 (OpenMP)

conda 의 MKL(`Library/bin/libiomp5md.dll`, 20240820)과 pip torch(`torch/lib/libiomp5md.dll`,
20260213)가 각각 Intel OpenMP 를 들고 와서, 나중에 로드되는 쪽이 프로세스를 중단시킨다
(`OMP: Error #15`). 어느 쪽을 교체해도 `control2026` 의 numpy 또는 torch 를 다시 빌드해야
하므로, `train_bc.py` 는 중복 로드를 허용(`KMP_DUPLICATE_LIB_OK`)하고 스레드 수를 4로 묶는다.
그 경고가 말하는 "조용한 오계산" 위험은 위의 `check_numpy_matches_torch()` 로 감시한다.
